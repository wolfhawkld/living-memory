## 1. 项目目标与使用背景

Living Memory 希望通过可视化知识图谱，持续外化、整合和巩固已经学过的知识与个人 insights，并在阅读、查询、回忆、使用、总结中维护可解释的学习状态。最终关注延迟后能否想起、解释、选择和使用知识，以及能否修正已有理解。

用户当前大量阅读 AI、数学概念，也学习其他兴趣领域；按空闲时间不定期观看在线视频以理解原理和应用。日常使用方式已经明确为**融入阅读、查询和工作，附带少量复习**。

已明确的两类痛点：

- **内容保持**：仍记得概念名称、全称与部分原理，但细节、推导、前提和边界逐渐模糊。
- **场景调用**：面对业务或研究问题，难以快速主动想到适用的已学概念；被提醒概念后可能恢复理解，但这与独立想起不同。

multi-agent orchestrator 的例子已经充分说明第二类痛点：用户希望能想到布尔逻辑、决策表、DAG、概率权重等曾学过的概念。该例作为需求背景保留，未将解决其工程架构纳入项目任务。早期偏离主线的建模讨论已标记为历史材料。

## 3. 记忆与遗忘研究所得

已整理记忆系统与遗忘理论、提取与迁移、可训练性三组研究，并形成[研究总结](research/consolidated-findings.md)。资料包括论文、综述与官方来源；部分来源只核对到摘要，当前不是完整系统综述。

目前采用的研究认识：

1. 即时表现、延迟保持与迁移应用需要分别观察。看完视频后觉得熟悉，不足以证明日后能独立调用。
2. 想不起可能涉及初始学习不足、线索不足、干扰或痕迹变化，不能由一次失败判定原因。
3. 给定名称解释概念与只给场景主动想起概念，是不同任务；提示条件应明确记录。
4. 主动提取、间隔、自我解释、比较相似概念与适用条件，是值得验证的训练方向，收益随材料和任务变化。
5. 可训练的方面包括知识的组织与编码、提取策略、问题表征与辨别、对掌握程度的判断；需分别检验具体知识、学习策略和未练任务上的迁移，不能承诺通用记忆能力全面增强。
6. 遗忘曲线的测量与拟合不能直接给出复杂个人知识的“剩余百分比”。系统只能依据表现和时间估计，不直接测量人脑记忆。
7. 点击、访问、查询、图谱边数或一次即时答对，都不足以直接更新为“已经掌握”。

需要继续研究与验证的部分包括个人间隔校准、新场景任务质量、误用与遗漏评价、长期学习效果，以及巩固、睡眠等未深入展开的机制。

## 4. 已设计的个人记忆强化流程

[流程 v0.1](design/personal-memory-workflow.md)已形成，用户认可大方向。

两条训练流程分别处理不同问题：

- **内容保持**：给定概念或具体目标 → 尝试解释/重建 → 对照资料和评价要点 → 区分遗漏、误解与提示依赖 → 记录表现 → 延迟后再检验。
- **场景调用**：先给场景，隐藏概念候选 → 表述问题结构并尝试提取候选 → 必要时逐步提供结构提示或名称 → 判断前提、边界和反例 → 对照反馈 → 在其他场景中再检验。

在场景任务里提前显示候选节点或答案会改变测量条件，因此该任务可以切到独立面板并暂时收起图谱。

| 日常入口 | 已提出的流程 | 设计目的 |
| --- | --- | --- |
| 阅读与视频 | 在自然停顿时尝试简短解释，记录原理、关系或适用条件，再对照来源 | 为内容留下有意义的提取入口 |
| 查询 | 可直接获得结果，也可自愿先尝试回忆；记录提示/查阅情况 | 兼顾工作效率与学习反馈 |
| 工作应用 | 记录问题特征、想到的候选、实际选择、使用结果和借助资料情况 | 连接真实场景与已有概念 |
| 总结与洞见 | 先重建理解，再补充遗漏、反例、关系与观点变化 | 整合知识并保留认知修正依据 |
| 少量复习 | 根据目标、近期表现与再访安排选择任务，可跳过或暂缓 | 控制额外负担，观察延迟保持 |

候选起步方案包括选 10–20 个概念、每天约 5 分钟额外练习预算，以及 1/3/7/14/30 天的透明间隔档位。这些是可修改的试用参数，不是用户已经确认的时间要求，也不是经过校准的最佳间隔。

## 5. 学习记录与图谱状态的设计

数据边界已形成：知识内容、学习事件、状态估计、任务选择、布局与宿主存储分别维护。本次建议在独立 Web 配套的单个本地服务中统一处理事件和持久化，供 CLI 与语音通道复用，不拆成多个微服务。

记录应能解释：针对哪个概念及内容版本、何时做了何种任务、允许了哪些提示、是否查阅或借助 AI、实际表现和反馈依据如何，以及估计为何发生变化。核心解释、细节/关系、场景调用、适用判断与实际使用分别保留证据，不把一个概念压缩为无法解释的单一掌握分数。

已写入流程的边界还包括：跳过或暂停不算失败，合理替代答案可成立，争议反馈暂不改变状态，同题即时纠错不重复计作独立延迟回忆；内容变化后需要检查旧题与旧表现是否仍适用。

候选视觉状态包括：

- 灰蓝/空心：尚未评估或证据不足。
- 青绿：近期有独立回忆证据。
- 琥珀：到了值得再次确认的窗口。
- 珊瑚：近期表现提示需要巩固。

这是内容保持视图中的初步表达，具体名称、色值和阈值仍可调整；场景调用使用相应的证据与图例。选中、查询路径和临时活动通过其他标记表达，避免覆盖状态含义。已有概念缺少本系统记录时允许保持“未知”，遗忘估计也不会删除知识或语义关系。

## 7. 可视化选型与设备性能

已比较 3d-force-graph / force-graph、Sigma + Graphology、G6、Cytoscape.js 与直接 Three.js 的能力、代价和主体许可。用户看过官方在线 Demo 后明确接受 **3d-force-graph + Three.js**，后续沿此方向推进。[技术选型与 Demo](research/visualization-options.md)

当前视觉方案包括：深色空间图谱、可调发光、操作触发的镜头聚焦、关联高亮、稳定布局、中文短标签、完整详情侧栏，以及平面阅读模式。布局稳定后保存位置；状态变化不重新打散图谱；动画强度与状态含义分开。

性能分析已覆盖布局计算、标签对象、节点/边几何、Bloom 后处理、高 DPI 和后台渲染。对应控制措施是布局冷却、局部展示、标签分级、限制内部画布尺寸、光效档位、隐藏暂停与关闭清理。

当前只有工程预期，没有实测帧率、内存、功耗或硬件门槛。后续需在目标设备上检查镜头操作、笔记输入响应与反复开关视图后的资源趋势。平面模拟仍可使用 WebGL，不能把它当成自动完成的轻量 Canvas 模式。

此前已核查 Obsidian 官方 ItemView/registerView、自定义视图生命周期、React 集成及笔记/元数据接口，作为后续宿主适配的依据。[载体研究](research/platform-options.md)

2026-09-16 用户明确选择先做独立 Web，再接 Obsidian；旧文档中优先插件的建议已被替代。TypeScript/React、本地服务和 SQLite 是本次工程方案，运行时兼容与语音连接需要先验证。

架构建议让记忆与任务逻辑、图谱组件、Obsidian 文件/工作区接口各自承担清楚的职责，保留将来换宿主的空间。开源需继续明确示例数据、导入导出、格式升级、重命名/拆分后的引用、依赖许可和发布方式；项目许可证尚未选定。AI、分享、同伴反馈与社交是扩展候选，不构成首版服务端、账号或信息流需求。

## 10. 下一阶段工作建议

当前首先按 [P0 五步](design/time-first-prototype.md#7-实现顺序与验收) 实现时间模型、最小数据和图谱，观察后再决定下一变量。以下是已定义但尚未启动的完整版本路线，不是 P0 的全部前置条件：

1. M0：优先核对记忆属性与估计规则，验证本地运行和真实语音访问，建立共同契约与样例。
2. M1：串起最小内容回忆闭环，能够保存提示/反馈、解释状态，并在重启后恢复。
3. M2：接入查询/生成、场景提取/辨别、少量复习、动态图谱和知识修正流程。
4. M3：验证语音/CLI/Web 一致性、性能与数据恢复，完成小范围基线和延迟试用。

尚待验证或认领的事项包括目标设备、运行时/SQLite 驱动、原生语音访问路径、记忆规则样例与试用参数、任务负责人。AI、同步、开源许可另行讨论；宿主、已给出的痛点、使用节奏与图谱技术不再重复澄清。
