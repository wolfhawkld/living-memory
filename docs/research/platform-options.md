# 技术载体、开源与扩展性：首轮研究

检索日期：2026-09-15。本文记录当前官方能力与待验证问题，不是正式架构决策。平台 API、政策和条款可能变化，开始实现或发布时应复核。

后续决定（2026-09-16）：用户已确认**先做独立 Web 原型，再接 Obsidian**。下文的优先插件建议保留为研究过程，不再代表首版宿主选择；当前架构见[首版技术设计](../design/technical-design-v0.1.md)。

## 当前判断

Obsidian 插件是值得验证的候选，尤其适合已有 vault、希望把学习任务融入笔记工作流的用户。是否适合本项目，仍取决于视觉交互、移动端、同步与用户现有工具。

用户已选择 progressive-kg 为首批材料，本地契约确认它使用 Obsidian Markdown 与链接结构；使用节奏也已明确为融入阅读、查询和工作。由此，复用现有知识库成为真实需求。最新视觉偏好为桌面优先、深色、突出空间纵深、较明显发光与镜头运动，当前建议直接验证 3D 自定义视图，并提供平面阅读模式。

在用户进一步询问实现框架、设备负担与插件可行性后，**现阶段建议优先把 Obsidian 桌面插件作为首个宿主原型**。这是基于已有笔记工作流与桌面需求的推荐，尚未得到插件实测，也不是用户已最终确认宿主。建议 TypeScript + React 管理搜索、详情与任务面板，在自定义视图中挂载 `3d-force-graph` / Three.js；保持记忆逻辑、图谱呈现与 Obsidian 数据接入的边界，以便未来复用。

官方已有在插件自定义视图中使用 React 的说明；可以据此组织界面挂载与卸载。[官方 React 集成文档](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Plugins/Getting%20started/Use%20React%20in%20your%20plugin.md) 结合图谱库接收普通 DOM 容器的接口，将 WebGL 图谱嵌入该视图具有实现依据，但本项目还没有完成嵌入验证。基础本地图谱与学习记录可以按离线插件设计，无须为此先搭建远程服务。

插件复用宿主的工作区，并不把 GPU 渲染转移到其他机器，也不自动降低图谱负担。需验证它与笔记编辑同时运行的输入响应，以及隐藏时暂停、再次显示时恢复、关闭时清理自建资源的完整生命周期。性能来源与控制方式见[可视化选型补充](visualization-options.md#9-界面框架与设备性能补充)。

应分别回答两个问题：**首个产品运行在哪里？核心逻辑需要多大程度脱离宿主？** “核心 + 适配器”是一种组织方式，可以用于插件或独立应用，不能直接当成第三种互斥的产品载体。

## 已核实的 Obsidian 能力

| 问题 | 第一方资料支持的事实 | 对项目的含义与未决点 |
| --- | --- | --- |
| 能否加入任务和知识入口？ | 公开 API 提供命令注册、Vault、MetadataCache、Workspace 等接口 | 可以研究笔记、链接与任务之间的衔接；笔记粒度是否适合概念与洞见仍需设计 |
| 能否做自己的图谱界面？ | 官方提供 `ItemView` 和 `registerView` 的自定义视图路径 | 可以在工作区内构建图谱；渲染性能、中文长标签、主题和编辑体验需实测 |
| 能否直接扩展原生 Graph View？ | 本轮公开 API 类型核查未发现 `GraphView` / `LocalGraphView` 导出，也未找到明确的专用公开扩展契约 | 不能据此断言所有集成都不可能；应将原生图谱扩展列为单独研究项，自定义视图是已有官方说明的路径 |
| 如何保存状态？ | `loadData` / `saveData` 提供插件 `data.json` 存取；API 提供外部设置变化处理；配置目录可变 | 这些接口不自动解决学习事件合并、数据版本与冲突；存储格式仍未选定 |

上述 API 事实来自[官方公共类型定义](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)；自定义视图生命周期与注册方式见[官方 Views 文档](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Plugins/User%20interface/Views.md)。

移动端无法使用桌面 Node.js / Electron API；依赖这些 API 的插件应声明仅桌面可用。应优先评估宿主的文件抽象，目标包含手机时需要真实设备验证。[官方移动端开发文档](https://docs.obsidian.md/Plugins/Getting+started/Mobile+development)

Obsidian Sync 对配置、社区插件安装与启用状态有独立选项，部分需要逐设备设置。文件同步不等于动态学习状态已经具备正确的并发合并语义；离线双端修改和外部变更回载需要实测。[官方 Sync 设置说明](https://obsidian.md/help/sync/settings)

## 宿主候选比较

下面的成本判断是工程分析，尚未得到原型测量。

| 选择 | 可以利用的能力 | 需要自行解决或验证的成本 | 哪些需求会让它更值得优先验证 |
| --- | --- | --- | --- |
| Obsidian 插件 | 笔记库、文件链接、元数据、工作区、命令与自定义视图 | 宿主耦合、主题适配、移动端差异、插件状态同步、分发与升级 | 用户已有 Obsidian 工作流；首版聚焦个人笔记与学习任务 |
| 独立应用，研究本地优先方案 | 可以自行定义工作区、交互、存储与发布体验 | 编辑、导入导出、索引、跨设备、分发与维护工作更多 | 视觉与移动体验需要较大自由度；希望使用者不依赖 Obsidian |

社交并不直接决定必须采用独立应用：两种宿主都可以进一步研究分享或协作服务。也不应因为未来可能有社交，就让首个个人学习闭环依赖账号或服务器。

本地优先是值得评估的设计方向，尚未被用户确认为强制要求；离线能力、数据控制与同步体验需要一起讨论。

## 值得保留的逻辑边界

以下是为了研究可迁移性而提出的候选边界，不要求立即建立独立包、服务或插件系统。

| 边界 | 需要能独立解释的内容 | 为什么值得验证 |
| --- | --- | --- |
| 知识内容 | 来源、概念、论点、关系、洞见版本 | 一篇笔记可能包含多个知识项；拆分与合并不能丢失来源 |
| 学习记录 | 任务、提示条件、回答、反馈与实际应用 | 后续状态估计应能追溯到行为；不同用户可学习同一内容 |
| 状态估计与任务选择 | 预测对象、输入证据、版本、下一步建议 | 便于比较简单安排和不同模型，不把调度器锁进视图 |
| 视图与交互 | 状态如何解释、知识如何探索和编辑 | 同一内容可以使用图谱、列表或文字回忆界面 |
| 宿主与存储适配 | 文件读写、命令、设备能力、导入导出 | 便于验证核心能否脱离 Obsidian 运行和恢复 |
| 可选扩展 | AI 出题与反馈、分享、同伴讨论、同步 | 应明确各自使用哪些内容和记录，再决定接口 |

初期可以在单个应用或插件内部保留这些边界。只有出现实际替换需求、稳定契约或第二个消费者后，再决定是否抽取共享库；不预先承诺同时维护两个完整客户端。

## 开源要明确的事项

插件代码的许可证与 Obsidian 宿主许可需要分别处理。官方目录政策要求插件明确许可证并处理依赖许可等事项；宿主条款将第三方插件与 Obsidian 软件分开描述。开源插件不意味着宿主也随之开源。[社区插件政策](https://docs.obsidian.md/community-directory/developer-policies)、[Obsidian 条款](https://obsidian.md/terms)

项目尚未选择许可证，也没有创建许可证文件。后续应在实际依赖和分发方式明确后记录选择。开源可用性还需要研究：

- 从一份示例数据开始，普通使用者能否复现安装、运行和升级。
- 内容、类型化关系、个人任务记录与状态估计能否完整导出及恢复。
- 格式升级、节点重命名/拆分/合并，是否会破坏来源与学习历史。
- 贡献者能否独立添加任务或呈现方式，且不必改变数据含义。
- 是否提供可读的格式说明、示例和迁移记录。

这些是项目设计议题，不是本轮已实现的能力。

## 决策前的原型检查

1. **交互**：在一个自定义视图内完成定位、打开来源、关系编辑、回忆与反馈，检查布局稳定性和长标签。
2. **数据**：记录一次带提示的任务，重启后恢复，并把内容及任务历史导出后重新导入；验证关系和引用未丢失。
3. **内容变化**：重命名、改写、拆分或合并笔记/概念，观察学习记录如何关联，如何发现题目失效。
4. **设备**：按用户确定的目标设备测量加载、触摸、渲染和编辑；使用代表性规模，记录节点/边数量与设备条件。
5. **同步**：若首版需要多设备，测试离线并行修改、重复事件、时钟偏差、外部变更和恢复，不默认一个 JSON 文件就足够。
6. **可替换性**：让候选核心逻辑读取同一份示例内容和任务记录，在不启动 Obsidian 的条件下产生可解释结果。

原型结果应写成简短决策记录：触发需求、候选、观察证据、选择与代价、什么变化会使决定需要重审。此时再确定框架、存储、图形引擎和调度器。
