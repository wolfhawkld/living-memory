## 先把功能描述转成可问清的问题

下表是工程建模候选，不是每个模块必须使用的实现方式。

| 功能 | 需要先明确的数学对象或问题 | 候选与成立条件 |
| --- | --- | --- |
| 意图识别 | 输入如何映射到目标、参数与约束？输出空间是否固定？ | 固定类别可以作为分类；组合目标和参数可作为结构化预测/语义解析。若存在歧义，需要保留不确定性并决定是否澄清 |
| 规则校验 | 请求是否在服务范围内？按安全政策是否允许处理？无法判断时如何分流？ | 服务范围分类、风险分类与确定性准入门控；误放与误拒代价不同可研究代价敏感决策，不确定时可研究选择性预测 |
| 上下文记忆 | 什么必须持续维护，什么需要按问题找回，什么能放入当前上下文？ | 分别研究状态更新、索引与检索、预算内内容选择；检索相关性不自动决定事实有效性或优先级 |
| 多 agent 协调 | 由当前状态和事件选择哪些动作？是否有并行、重试与取消？ | 已知转移和分支可用状态机/状态图；若要根据目标自动寻找动作序列，再研究规划 |

事件、转移、层级及并行状态的正式例子见 [W3C SCXML](https://www.w3.org/TR/scxml/)。按安全类别判定请求的研究例子见 [Llama Guard, 2023](https://arxiv.org/abs/2312.06674)；允许分类器在部分输入上暂不作答、研究错误风险与覆盖率权衡的例子见 [SelectiveNet, 2019](https://proceedings.mlr.press/v97/geifman19a.html)。这些是问题形式的参考，尚未选择具体模型。

## 将语义判定与强制准入分别建模

令 `x` 为请求，`c` 为相关上下文；以下符号还隐含当前服务范围定义和安全政策：

```text
D(x, c) ∈ {范围内, 范围外, 待确定}
R(x, c) ∈ {通过, 阻断, 待确定}
放行进入业务执行 = (D = 范围内) AND (R = 通过)
```

这是本案例的候选决策表达，不是已验证的检测算法。`D` 与 `R` 表示系统的判定，不代表真实标签必然正确；可以由规则、分类模型或组合方法产生。相关请求仍可能有风险，无风险请求也可能超出服务范围，所以需要分别保留这两个判断，不能假定其统计独立。

“强校验”体现为执行路径必须遵守准入结果。语义分类仍可能误判，门控的确定性无法消除上游判定错误。服务范围外由产品职责定义，不等同于统计上的分布外（OOD）；分类器暂不判断（abstain）也不等同于拒绝用户，后续可按政策进入澄清、复核或其他受限响应分支。

若引入概率与阈值，应在代表性数据上评估误放、误拒及不作判定的比例，并依据具体代价选择策略。模型自报的置信度不能直接视为校准概率。此处只讨论请求准入；输入通过不能自动证明后续输出或动作满足所有要求。

Schema/类型检查解决数据结构问题，SAT/SMT 处理已形式化的约束；它们不是用户此处自然语言范围与风险判定的首要抽象。

## 准入判断与任务状态决策如何衔接

可以先作如下工作性抽象：

- `s_t`：当前任务记录，例如准入结果、目标、已完成步骤、已验证事实、待解问题与资源使用。
- `a_t`：一个动作，例如请求澄清、委派子任务、调用工具、汇总、重试或结束。
- `o_(t+1)`：动作后获得的结果或外部事件。

```text
动作选择     a_t = π(s_t)
记录更新     s_(t+1) = F(s_t, a_t, o_(t+1))
```

这里 `π` 只是动作选择规则的抽象，可以由显式规则、搜索、LLM 或组合方式实现；`F` 表示状态更新约定。业务执行分支须满足前述准入条件，其余判定结果进入各自的处理分支。这些记号并未假定当前记录包含世界的全部信息，也未假定马尔可夫性质或已经确定最优策略。

这一框架帮助放置原需求：意图识别形成候选目标，范围与风险判定支持准入门控，记忆提供任务记录与参考信息，协调策略选择下一步。接下来才决定哪个部分需要更具体的算法。

## 什么时候才值得研究更复杂的决策模型

若问题包含不可直接观察的状态，需要通过提问或动作获取信息，且有可定义的转移、观测和奖励/成本模型，可以研究 POMDP。它使用对隐藏状态的信念表示来支持序贯决策；仅存在模糊自然语言或 LLM 不确定性，尚不足以完成这种建模。[Kaelbling, Littman & Cassandra, 1998](https://doi.org/10.1016/S0004-3702(98)00023-X)

要判断该候选是否值得投入，应具体回答：隐藏的是什么？什么行动能改变信息？成本如何衡量？模型能否获得？规划相对于明确的状态转移会带来什么可验证收益？

## “上下文有限”提供的另一条建模入口

假设已知候选信息集合 `H`、当前任务 `q` 和预算 `B`，可以将选择上下文 `M` 写成一种工作性优化问题：

```text
选择 M ⊆ H，使 U(M; q, s_t) 尽可能大
约束：token_cost(M) ≤ B，且包含当前任务要求的必要信息
```

这是本轮的形式化示例，尚未指定或估计效用函数 `U`。条目之间可能互补、重复、冲突，顺序也可能影响结果。只有在价值可加、成本等假设成立时，才适合进一步简化成常见背包形式；实际也可能需要集合或序列建模。

## 用这个案例继续研究人的知识调用

可保留三份不同表现：

1. 只看原始需求时，自己如何描述问题、想到哪些候选。
2. 得到“输出空间、状态、动作、约束、信息预算”等结构提示后，新增了什么想法。
3. 得到“分类、选择性预测、决策理论、状态机”等名称后，能否解释适用条件、实例化对象并指出不适用情况。

结构提示或候选名称改变了任务，后两步不能计为第一次的自发提取。一次提示奏效也不能唯一确定瓶颈，但可以形成下一轮的研究假设。

后续可比较表面不同的案例，例如 orchestrator 与有前置依赖的订单处理流程，先找共同的状态、事件与约束，再解释重要差异。还要研究某种形式化何时没有必要：例如一次性的纯文本改写是否真的需要复杂规划。对比应帮助判断模型用途，并以新案例检验，不能只背“orchestrator 对应某算法”。
