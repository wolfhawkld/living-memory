# 图谱可视化分析与技术选型

日期：2026-09-15。基于用户认可的[记忆强化流程](../design/personal-memory-workflow.md)，核查官方文档与代码仓库，形成可进入原型验证的选择。视觉语义与交互见[可视化体验 v0.1](../design/visualization-spec.md)。本轮没有进行候选库的性能基准或 Obsidian 集成测试。

## 1. 结论与选择范围

**已确认的技术方向：`3d-force-graph` + Three.js 实现桌面 3D 图谱，以深色空间、发光、镜头聚焦和关联高亮作为实现基础。** 外围使用普通网页 UI 承担搜索、文字详情与任务；继续保留同一图谱增加平面阅读模式的设计。`force-graph` 为独立 Canvas 2D 备选，初版不必同时维护两个渲染器。

确认记录：2026-09-15，用户查看官方 Demo 后回复“效果非常不错，那就定这个方向吧”。可视化方向由初选建议转为用户确认，后续按此推进具体实现。精确库版本、光效参数、中文标签策略及性能仍需在原型中验证；普通 UI 的 React 方案与 Obsidian 宿主仍是推荐，未将此次视觉确认扩大为对其他架构选择的确认。

主要理由是用户希望空间体验成为重要组成部分；该组件已有镜头过渡、自定义 Three.js 对象和后处理入口，能直接进入三维体验验证。需要自行承担的主要部分是中文标签避让、状态编码、键盘/文字替代入口和空间/阅读模式的一致性。官方提供 `cameraPosition` 与 `postProcessingComposer`，并有 Bloom 示例；选择性发光与状态色保护仍需实现和验证。[3D 组件文档](https://github.com/vasturiano/3d-force-graph)

后续按已选方向推进；若出现下文列明的实际瓶颈或需求变化，再针对性重评候选。若强调复杂图编辑、丰富内置交互与多种业务布局，重评 G6；若主要压力变成大量节点的 2D 总览和图分析，重评 Sigma + Graphology。

## 2. 将可视化拆为四项选择

| 层次 | 本项目需要决定什么 | 当前方向 |
| --- | --- | --- |
| 视觉与交互 | 什么保持稳定、什么随操作变化、颜色代表什么 | 深色空间星图、发光、受控镜头、平面阅读模式 |
| 渲染 | 如何画节点、连线、标签和选择反馈 | 以 Three.js/WebGL 图谱组件为主，Canvas 2D 为备选 |
| 布局 | 节点位置如何生成、保存和局部更新 | 可停止的力导向布局，保存坐标与固定锚点；特殊子图另选布局 |

## 4. 为什么先选 3d-force-graph

### 可直接检验当前体验问题

三维组件提供 Three.js 对象、镜头和后处理定制入口，用来验证空间聚焦、发光和状态标记。布局仍可冷却和固定；具有镜头运动不意味着节点必须持续移动。独立 2D 组件的 Canvas 定制和交互能力作为以后对照，不先为它复制整套界面。这些能力来自组件文档，未证明最终设计已经实现或性能合格。

为保护笔记内容和个人事件，应给渲染/模拟提供单独的视图数据；布局模拟可能修改节点坐标与关联对象，不让这些临时变化直接改写知识记录。稳定 ID 用于选择和回溯，位置与学习状态分别维护。[D3 模拟的数据修改说明](https://d3js.org/d3-force/simulation)

### 平面阅读模式需要明确设计

优先在同一组件中提供平面布局及固定正面视角：保留平移、缩放、搜索和选择，阅读时限制旋转并降低光效。空间和平面坐标快照分别保存，切换时保留当前概念；是否需要正交镜头、以及如何通过公开接口实现，需单独验证，不能只改一个参数就宣称完成二维交互。

`numDimensions(2)` 控制模拟维度，底层仍是 WebGL/Three.js 场景；它不等于 Canvas 2D，也不自动完成阅读模式。若以后改用独立 `force-graph`，其 Canvas 回调与 Three.js 对象各自实现，共享业务含义与数据约定，不能零成本互换。

### 目前不需要自建完整 Three.js 图谱

先用组件定位哪些自定义确实无法满足需求，再决定是否下沉到 Three.js。即使要定制三维节点，也可以先使用组件对象扩展入口，不必立即自行实现所有布局、拾取和镜头行为。

## 5. 标签、稳定布局与动态状态的实现约束

- **标签是选型关键。** Canvas/Sprite 能绘制中文，不等于自动解决长名称、字体加载、碰撞、缩放与高 DPI 清晰度。用真实样式测试，不只看官方短英文标签例子。
- **布局停止和界面停止是两件事。** `force-graph` 的 `pauseAnimation()` 文档说明会冻结渲染并取消交互；日常稳定视图应使模拟冷却、固定坐标或使用预计算布局，同时保持点击、选择和缩放可用。不要把整个组件暂停当成固定节点的方案。[force-graph 渲染控制](https://github.com/vasturiano/force-graph#render-control)
- **状态更新不驱动节点位置。** 回忆结果改变颜色和详情；不会重新启动全图力模拟，也不会因“遗忘”而让节点远离、消失或减少语义关系。
- **长段文字不做空间对象。** 图上保留短标签与局部关系，正文、公式、来源和学习历史进入普通 DOM 面板；三维标签另测遮挡与缩放。
- **状态色需要跨光照保持可辨。** 选择独立状态标记或不受光照影响的绘制方式，比较三维材质、色调处理和背景合成后实际颜色；不能只验证配置中的十六进制值。
- **动态效果按事件发生。** 冷却后的空闲状态仍需处理必要重绘；查询路径与选择反馈按需运行。特效不得改写学习数据。
- **可访问入口由应用补齐。** 提供可搜索的文字结果、节点列表、键盘选择和清楚的状态描述；不要假设 Canvas/WebGL 图天然具备这些能力。

## 6. 与 Obsidian 和开源扩展的关系

可视化组件先接受一个普通页面容器及明确的数据输入，不依赖 Obsidian API 读取个人内容。宿主负责提供知识引用、打开原文、保存布局与学习事件；图谱只展示与触发动作。

Obsidian 路线若成立，优先通过公开自定义视图验证，而不是预设原生 Graph View 的私有结构可扩展。本轮并未完成宿主加载、卸载、重开、主题变化或移动端验证；官方能力与此前核查边界见[载体研究](platform-options.md)。

同一数据可以提供图谱、列表或回忆界面。初期在一个应用内部保持职责清楚即可，不为未来可能的扩展先拆一组服务。插件代码开源、用户知识内容共享、个人表现记录共享是不同决定。

## 7. 原型验证顺序与换型条件

| 阶段 | 输入与操作 | 必须回答的问题 |
| --- | --- | --- |
| 风格预览 | 固定示例图，切换气质、搜索、选中、演示路径与关闭动画 | 气质是否合适，中文和状态能否读懂；不用于性能结论 |
| 3D 引擎原型 | progressive-kg 的代表性小子图及全量概念索引；原型前确认实际边数与类型 | 中文标签、遮挡、聚焦镜头、发光与状态色、固定布局和恢复是否成立 |
| 对照压力测试 | 例如 1,000 点/4,000 边与 5,000 点/20,000 边的明确标记合成图，含长中文标签与不同密度 | 记录布局耗时、交互帧时间、内存与空闲负担；规模为测试样本，不是产品承诺 |
| 平面阅读对照 | 相同概念与状态，固定正面视角、独立平面位置快照、降低光效 | 用户是否容易读关系、长标签并回到三维焦点；必要时再加 Canvas 对照 |
| 宿主验证 | 在选定宿主中打开、改变大小、关闭、重新打开 | 生命周期、资源释放、字体、主题、离线和输入体验是否一致 |

当前快照已有约 216 个概念页；这不包含充分的边密度、子目标数量和最终显示对象统计，不能由节点数单独承诺性能。测试记录要写明设备、浏览器/宿主、视口、像素比、标签数量、关系密度和效果开关。

重评条件：

- 若主瓶颈是二维大图渲染，使用相同数据与样式对照 Sigma，避免将不同特效负担造成的差异误认为库性能。
- 若中文标签与交互行为需要大量自建，同时用户要求丰富图编辑，则与 G6 做同任务对照，并检查其 3D 扩展是否满足相同语义。
- 若核心需求转为关系算法与复杂子图操作，比较 Cytoscape.js 或独立图数据/算法层。
- 若选定组件无法提供必要的三维控制，再论证直接 Three.js 的实现成本。

首轮验收关注：搜索可找到完整中文名；点击与键盘选择一致；状态改变不重新布局；减少动画后功能保留；场景练习不会泄漏候选；布局恢复与数据重命名可以正确关联。具体帧率门槛在目标设备明确后设定，当前不报告未测结果。

## 8. 本轮产出与证据范围

本轮提供官方能力比较、明确的原型优先路线、视觉编码方案及一个离线风格预览。预览采用原生 HTML/CSS/SVG，未使用上述候选图谱库；它帮助评审视觉取舍，不证明已经完成库接入、真正三维渲染或大图性能验证。

## 9. 界面框架与设备性能补充

2026-09-15，用户追问最佳实现框架、浏览器设备压力及能否直接做 Obsidian 插件。以下为工程建议，尚未固定依赖、实现或完成性能测试。

推荐组合是 **TypeScript + React（普通界面）+ 3d-force-graph / Three.js（图谱）**。React 管理搜索、筛选、概念详情、任务表单等界面；图谱通过独立容器挂载。图谱引擎自己维护每帧坐标和相机，避免把每一帧节点位置放进 React state，造成整页频繁更新。实例引用可以保存在 ref 中；改变 ref 本身不会触发 React 重渲染。[React ref 文档](https://react.dev/reference/react/useRef)

选择 React 是针对未来多个交互面板与组件复用的维护判断，不是已测出的性能优势；轻量原型仍可使用原生 TypeScript。图谱组件没有强制要求 React。记忆事件、状态估计与任务逻辑用不依赖 React 或 Obsidian 的 TypeScript 模块组织，宿主负责内容读取与持久化；目前不需要拆成多个独立服务。

### 设备压力的来源

| 负担 | 主要来源 | 设计上的控制手段 |
| --- | --- | --- |
| CPU | 力导向布局、命中检测、索引及过多界面更新 | 布局稳定后冷却并保存坐标；知识或布局必要变化时才重算；索引增量更新 |
| GPU | 节点/边几何、透明光晕叠加、Bloom、多次后处理与高像素画布 | 限制内部渲染分辨率、几何精度与发光范围；提供效果档位；省电档关闭 Bloom 改用简化光晕 |
| 标签与内存 | 大量中文标签对象/纹理、重复创建场景、未释放资源 | 只显示焦点、邻域与必要标签，正文留在 DOM 侧栏；复用并清理自建资源 |
| 持续耗电 | 长时间动画与隐藏视图继续渲染 | 镜头按操作短时过渡，隐藏后暂停、恢复可见后继续；关闭视图时结束任务并释放资源 |

后处理通常包含多个 Pass 与中间渲染目标，Bloom 会进行模糊与叠加。相同 CSS 尺寸下，渲染像素比从 1 提升到 2，像素数变为四倍；这不意味着总耗时必然四倍，但说明高 DPI 是重要变量。[Three.js 后处理说明](https://threejs.org/manual/en/post-processing.html)、[高 DPI 与绘制尺寸](https://threejs.org/manual/en/responsive.html)

当前约 216 个概念页是内容快照，不是最终节点/边/标签统计。在支持硬件加速的现代桌面设备上，几百个简单节点、受控标签与光效，是合理的原型目标；**这属于待测的工程预期，不能据此保证某款集成显卡、帧率、内存或续航**。节点增多或边变密时，应优先显示主题聚合及局部邻域。现有 18 节点 HTML/SVG 预览不能代表三维引擎性能。

需区分三个动作：冷却布局只停止模拟；关闭动画特效不必停止必要重绘；`pauseAnimation()` 会取消交互，适用于已隐藏的图谱，不能直接用于仍要点击的可见阅读视图。Web Worker 可作为重布局的后续优化，但不是当前图谱库自动提供的免主线程成本保证。[组件运行控制](https://github.com/vasturiano/3d-force-graph)

记忆状态按学习事件、视图打开与合理的时间刷新节奏更新即可；没有必要随着渲染帧率计算遗忘曲线。WebGL 资源的释放需按所有权处理：清理插件自建材质、纹理、几何、后处理与监听器，同时核实组件自身的销毁行为，避免遗漏或释放仍被共享的资源。[Three.js 资源清理](https://threejs.org/manual/en/how-to-dispose-of-objects.html)

验收应在同一目标设备比较浏览器与 Obsidian 自定义视图，记录初次布局耗时、镜头运动和输入时的帧时间、空闲/隐藏时负担、反复关闭重开后的资源趋势，以及旁边笔记编辑是否受影响。未获得这些结果前不宣称插件比浏览器更快或达到固定帧率。
