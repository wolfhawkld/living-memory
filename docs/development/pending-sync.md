# 待同步记录与错误定位

日期：2026-09-20。

离线或临时写入失败的记录保存在浏览器中，并按知识源隔离。学习记录和参数重试保留原请求内容、事件 ID、版本和实际操作时间；无效布局按下述规则先备份再修复。服务确认写入或返回幂等重复回执，并且浏览器成功清理队列后，该条目才计入同步成功。

## 页面行为

左侧「待同步详情」显示每条记录的类型、创建时间，以及上一次重试的错误信息和错误码。「重试同步」会更新这些信息，页面刷新后仍可查看。首次写入失败时尚未重试的条目显示「等待重试」。

重试结果分别报告成功和失败，不会因部分成功而隐藏剩余失败。请求失败不再一律显示「确认本地服务」；浏览器无法清理已写入条目的标记时，明确提示 `PENDING_STORAGE_FAILED`，不会将其描述为服务未写入。

同一页面、同一知识源同时触发手动重试和网络恢复通知时，共享一轮发送。此限制不覆盖多个浏览器标签页；重温和观察仍通过事件 ID 由服务保证幂等。原有会话令牌续期及知识源核对继续生效。

## 无效布局修复

本次用户反馈的实际错误是 `INVALID_LAYOUT` /「布局坐标必须是有限数字」。旧保存逻辑只检查 `typeof coordinate === 'number'`，会放过 `NaN` 和 `Infinity`；这类值序列化到 JSON 后成为 `null`，原样重试仍被服务拒绝。尚未读取浏览器原始条目，不能据此断定该条目中具体哪个节点或轴无效。

新布局保存要求每个位置的 x、y、z 都是有限数字，初始化遇到无效位置时使用既有默认布局。保存过程中跳过无效位置；API 发送前再次校验，阻止无效坐标进入新请求。

对旧队列，刷新页面后点击「重试同步」：

1. 只修复 `PUT /layout` 的坐标对象，顶层须为普通对象且总条目不超过 10,000。其他结构、数量错误继续保留并显示服务错误。
2. 先将原待同步条目、无效节点 ID 列表和修复时间保存到同知识源的浏览器恢复区，同一条目只备份一次。备份失败时不发送修复请求。
3. 只发送具有合法 x、y、z 的位置，不将空值转换成 0。服务按节点合并布局，未发送的节点保留服务端原位置；若原先没有位置，图谱使用默认位置。全部无效时发送空对象，服务布局保持不变。
4. 原队列内容在请求期间保持不变，仅在服务确认和本地清理均成功后移除。失败仍可重试；成功提示备份完成及跳过的位置数量。

原布局备份不随待同步项删除，位于 localStorage 的 `living-memory.layout-recovery.v1.<encodeURIComponent(sourceId)>` 键；值为数组，每项含 `write`（原条目）、`invalidIds`、`repairedAt`。该恢复区供后续排查使用，不自动恢复无效坐标，也不写入个人学习历史。清空站点数据会一并清除备份。

## 处理边界

| 错误 | 含义与后续处理 |
| --- | --- |
| `NETWORK_OFFLINE`、临时服务错误 | 恢复服务或网络后可重试 |
| `SOURCE_REVISION_MISMATCH`、`CONCEPT_NOT_FOUND` | 来源内容已变化或概念已移除，需要核对原记录，不能自动替换来源或目标 |
| `CONFIG_CONFLICT` | 参数版本已改变，需要核对当前设置，不能用新 revision 静默覆盖 |
| `EVENT_CONFLICT`、`ANCHOR_CONFLICT` | 事件内容或观察引用不一致，保留原记录供核对 |
| `SOURCE_MISMATCH` | 服务正在使用另一个知识源，旧记录不得发送到新知识源 |
| `INVALID_LAYOUT` | 无效位置可在备份后自动跳过；顶层结构或数量不合法仍需核对原布局 |
| `PENDING_LAYOUT_BACKUP_FAILED` | 原布局无法安全备份，尚未发送修复请求 |
| `PENDING_STORAGE_UNAVAILABLE` | 无法读取待同步队列，不按空队列宣告完成 |
| `PENDING_STORAGE_FAILED` | 服务已确认写入，但浏览器未成功清理本地标记 |

失败项保留原内容，新增的 `lastError` 只记录错误码、HTTP 状态、消息、是否可重试与尝试时间。学习时间、版本、来源和目标概念不会因布局修复而被替换。配置写入若已被服务接受但本地清理失败，下一次可能出现版本冲突，需要核对现有设置。
