# 关系建议的人工复核

更新：2026-10-12。LM-014B 在原应用 / 总结下面，独立记录关系建议的处理决定，并核对当前完整知识源。它接续[结构化关系建议](relation-suggestions.md)，与文字修正分别处理。

## 使用流程

1. 在真实记录、实时时间模式下选中主概念，展开学习历史中的应用 / 总结正文。
2. 含关系建议的记录显示「关系建议复核」。查看当前两端的名称、路径、资料版本，以及原关系和建议关系是否存在。
3. 经原 progressive-kg 流程修改知识源并刷新后，重新核对。新增要求建议关系存在；修改要求原关系消失且建议关系存在；删除要求原关系消失。两端都必须仍能定位。
4. 结构符合时，选择「人工确认已采纳」，勾选已核对并保存。也可直接记录「暂不采用」或「待处理」，保留说明。
5. 下方保留每次决定、当时双端和关系依据。当前依据变化会提示重新核对，不覆盖旧决定，也不自动撤销或确认采纳。

关系按方向、类型和完整描述精确核对，来自全量知识索引，不受页面显示节点上限影响。两端任一缺失时，关系状态为未知，不能把缺失节点解释为删除成功。主概念正文版本不变也可核对：关系或另一端可能已更新。结构符合只表示可供人工确认的依据，不等于建议正确或已被本人接受。

文字与关系的处理决定互不替代。复核仅是知识维护，不改变重温起点、H、回忆成绩、信心统计、复习预算或本人长期保持；不调用 LLM、不写源知识，也不为另一端复制应用记录。

## 并发与失败恢复

首次提交固定事件 ID、发生时间、前一决定、说明和双端 / 关系依据。保存前服务端再次核对当前来源和处理链；变化返回冲突，不能静默覆盖。已接受的原样重试先确认重复，不因后来来源或处理链变化而失效。

- 保存成功后读取失败，仍可只读刷新核对历史。
- 网络中断或结果未知时，保留原请求，只能原样重试确认；不能借重新核对生成新的决定。待同步请求按账号知识空间保存。
- 首次请求明确收到 `RELATION_REVIEW_SOURCE_CHANGED` 或 `RELATION_REVIEW_CONFLICT` 时，可显式重新核对，再提交新的决定；同事件内容冲突不能据此重建请求。
- 已在待同步队列的上述两类明确冲突，可先「保留备份并撤回请求」，再返回原记录重新核对。浏览器备份使用现有 `living-memory.correction-recovery.v1.<encodeURIComponent(sourceId)>`，保留原路径与完整请求，不属于服务端 JSON。

未提交说明保存在当前页面内存；切换节点、收起记录或刷新页面前应保存。编辑文字或关系复核期间都暂缓自动刷新，两个表单分别维护编辑锁。

## 数据与恢复

`GET /api/applications/:applicationEventId/relation-review` 返回当前依据和最近 50 次决定；`POST /api/relation-reviews` 追加独立决定。都限制在当前账号 / 知识空间，写入还需要有效本机会话令牌。

SQLite 加法新增 `relation_reviews` 表，旧应用、文字复核及原始请求保持原样。学习 JSON 仍为 `schemaVersion: 1`，非空时增加可选 `relationReviews`，导出保留全部事件和当时依据。旧备份缺失该字段视为无关系决定。

导入检查原应用、主概念、双端身份、精确关系语义、事件冲突和前序链；端点只映射一次，历史名称 / 路径 / 版本与存在状态不重算。缺失父记录、分叉、循环、时间错误或非法已采纳依据会阻止整批恢复，事务失败整批回滚。导入不要求当时依据仍符合今天的知识源。

含 `relationReviews` 的新备份须用本轮或更新程序恢复；网页与后台同步更新。更新前备份账号与学习数据库，回退按[完整恢复步骤](../releases/upgrade-and-recovery.md)，不依赖旧程序保留新增数据。

## 验证与人工试用

自动检查使用合成知识、隔离账号与临时数据库，覆盖精确关系、缺失端点、处理链、重试、账号隔离、旧库迁移、导入映射和事务回滚。远端浏览器回归检查表单与失败恢复；不运行本地浏览器。最终测试结果记录于[迭代 TODO](../planning/iteration-todo-2026-09-22.md)。

本人可用一条关系建议测试「暂不采用 → 待处理」，再经原 KG 流程更新关系、刷新并确认采纳，检查历史保留与节点记忆时间。真实关系正确性、视觉体验和外部 KG 完整流程仍待本人验证；跨概念传播与独立关系待办总览未包含在本项。
